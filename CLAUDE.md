# CLAUDE.md — NewFile

NewFile is a native macOS utility (app + Finder Sync extension) distributed as a signed, notarized DMG and via a Homebrew tap. Craft track — judged by the craft-track bar (used ≥30d / teaches a skill / scratches a real irritation), **never** by the commercial Verdict Machine.

## The two-repo rule (most common mistake)

**Every release touches TWO repositories:**

| Repo | Holds |
|---|---|
| `mariusgm/newfile` (this one) | app source, `project.yml`, the built DMG under `release/` |
| `mariusgm/newfile-site` | the marketing site **and the Sparkle appcast** |

Shipping a version here without updating the appcast in `newfile-site` means existing users never receive the update. The site deploys on **Cloudflare Pages** (CF CI auto-deploys on push) — not Vercel. There are no GitHub Actions workflows in this repo; do not look for release CI here.

## Public repo boundary

This repo is public. Publish reproducible build steps and the identifiers a build or uninstall requires, such as the Team ID. Keep machine names, account details and keychain profile names in the private hub. Check the PR diff and release assets for them before publishing.

## Build

Project is generated by **XcodeGen** from `project.yml` — edit that, never the `.xcodeproj` directly (it is regenerated and your change is lost).

```bash
xcodegen generate          # regenerate NewFile.xcodeproj from project.yml
xcrun xcodebuild -scheme NewFile -configuration Release
```

Version lives in `project.yml` (`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`), currently 0.2.5 / 8, Swift 5.10. Latest tag is `v0.2.5` (released 2026-11-16). `release/` carries the archive, DMG, `ExportOptions.plist`, `resume-notarization.sh` and a per-version runbook — read the runbook before cutting a release.

## Release mechanics (verified 2026-09-02, v0.2.2)

- Notary keychain profile: the previous profile **returned HTTP 401 on 2026-10-06** and re-storing it from the ASC API key did not take effect (unexplained; repair deferred). v0.2.4 notarized with a working profile from the same team; its name and key are in hub `services/app-store-connect-api.md`. Sparkle EdDSA key: keychain service `https://sparkle-project.org`, so `sign_update --account newfile` (default account fails).
- **Codesign the DMG before notarizing** (`codesign -s "Developer ID Application: …" --timestamp NewFile.dmg`), then submit → staple → `spctl -a -t install` = accepted. v0.2.1 and earlier shipped UNSIGNED DMGs (spctl rejected; worked only via the stapled ticket) — v0.2.2 is the first to pass Gatekeeper assessment.
- **Sandboxed host + Sparkle needs the mach-lookup exceptions** (`<bundle-id>-spks` / `-spki` in `App/NewFile.entitlements`). Without them every update dies with "installation data was never received" (bootstrap lookup denial, xpc error 159) — auto-update was broken from v0.1.0 until v0.2.3, and 0.2.1/0.2.2 users must update manually once. Test any updater change against a loopback appcast (serve a signed zip + appcast on localhost, `defaults write` SUFeedURL into the app container) BEFORE publishing.
- **Kill the old app process before install-testing a new build** — `osascript quit` fails silently when a dialog is up; a stale process runs the old binary and invalidates the test (`pkill -9 -f NewFile.app`, then verify pid churn).
- **Publish TWO assets per release — the appcast enclosure must NOT point at the DMG.** Through v0.2.3 the appcast enclosure pointed at the same `NewFile.dmg` humans download from the site, so Sparkle's automatic background updates incremented the *identical* GitHub download counter as first-time installs, and the two are not separable from GitHub's API. From the next release on: `NewFile.dmg` for humans / Homebrew / newfile.dev, and a separate `NewFile-update.zip` (zipped `NewFile.app`) as the appcast enclosure only. Sign the zip with `sign_update --account newfile` and use its own `length` + `sparkle:edSignature` in the appcast item. This splits the counters permanently: DMG count = manual-download traffic (still includes repeat downloads and reinstalls — not an install count), zip count = automatic update traffic. Do not "simplify" it back to one asset — the single-asset shape is what corrupted the traction series on 2026-09-02.
- **Release order (v0.2.4 onward):** archive → Developer ID export → zip the app, notarize, `stapler staple` the **app** → from that one stapled app make BOTH artifacts: `ditto -c -k --keepParent NewFile.app NewFile-update.zip` (Sparkle enclosure, signed with `sign_update --account newfile`) and the DMG (`create-dmg`, codesign, notarize, staple). The ZIP that passes the loopback test is the exact file that gets published — never regenerate it after testing.
- **Rollback before any install test:** `ditto` the installed app to `~/Backups/newfile-<ver>-rollback/` and `codesign --verify --deep --strict` the copy. Settings live in `~/Library/Group Containers/Q7VD7MTRL8.dev.newfile.NewFile/` and `~/Library/Containers/dev.newfile.NewFile/` — **the Claude Code shell cannot read either (TCC; `defaults export` returns an empty dict)**, so the operator quits NewFile and copies the Preferences folders in Finder.
- **Loopback update test — the SUFeedURL override must be written by the operator in Terminal.app** (same TCC wall): first `defaults read <container prefs path> SUFeedURL` to record any existing override, then write the localhost feed, test, and `defaults delete` (or restore) afterwards; confirm the app is back on `https://newfile.dev/appcast.xml`.
- sign_update lives under DerivedData `SourcePackages/artifacts/sparkle/Sparkle/bin/` — deleting DerivedData removes it until the next build.

## Known traps

- **App Group IDs need the Team-ID prefix.** Omitting it makes macOS re-prompt for permissions on every launch. This was the fix that shipped in v0.2.1 — do not regress it.
- **Notarization entitlement debt:** the appex ships a broad temporary exception entitlement. It notarizes today, but it is the most likely cause of a future slow-lane review or rejection. Treat any notarization slowdown as this, first.
- **No Resend, no email in this repo** (verified 2026-07-13). If a task seems to need transactional email, it is the wrong repo.

Primary: GitHub DMG + Homebrew tap `mariusgm/newfile` (free, open source).

## Roadmap

### Next release after 0.2.5 — template editor and Settings improvements (operator, 2026-11-16)

**Scheduled scope, not implemented:** native Find/Replace in the existing template sheet, literal plain-text input (no automatic quote/dash substitutions or autocorrection), and reliable native undo/redo. Small secondary Find affordance + Command-F; retain Save/Cancel/Remove and the existing template data format. First verify build 8's native behavior so existing capabilities are not reported as missing. Prefer platform controls with no editor dependency.

Spec and acceptance checks: [Template editor basics](docs/specs/2026-11-16-template-editor-basics-design.md). Target is the next release after 0.2.5 (8), released 2026-11-16. The operator named it **0.2.6** on 2026-11-21: #27 together with this editor work, and #27 does not ship alone. No release date is assigned here. Syntax highlighting, line numbers, formatting toolbar and template variables remain deferred. No code or release change is included in this roadmap entry.

**Additional next-release scope (operator, 2026-11-16), in priority order:**

1. **Protect saved custom types during invalid edits.** **Reproduced on v0.2.5 (`b0c34a3`), 2026-11-18; the fix is implemented in #27; its release walkthrough is pending.** The defect: `PreferencesViewModel.validOnly` filtered invalid extensions out of the persisted list, so clearing or invalidating a saved custom type's extension, then letting the debounce fire or closing Settings, removed that type and its template from the store with no undo. #27 routes both write paths through `Shared/FileTypePersistence.entriesToSave(edited:lastSaved:)` and adds an inline caption while a row is held; unit tests pass, and the caption has not yet been checked visually in the running app. The contract: keep the last valid saved entry while its edit is invalid, show an inline explanation, and commit the updated entry once valid. A new never-valid row must not enter the Finder menu. Deliberate deletion must still work. Acceptance: edit an existing custom type with a template to an empty/invalid extension, wait past the debounce, close/reopen Settings, and confirm the original saved entry and template remain; then correct the extension and confirm the valid edit persists. Keep this a focused persistence fix, not a new draft-management system.
2. **Preview the resulting filename.** Show a small secondary example derived from the same filename-generation logic used by Finder: `Creates: Untitled.R` or `Creates: .env · hidden file`. Update it with extension/default-filename edits; show no valid-result claim for invalid input. The example assumes no filename collision; actual files still use the existing numbering rule. Acceptance: ordinary names, blank base names/dotfiles, uppercase extensions and a base name already containing its extension all match the first filename Finder would create. No extra main screen or duplicate naming algorithm.
3. **Optional if small: confirm deletion of a custom type containing a template.** Name the type in a native confirmation with Cancel as the safe action; confirm before removing the row or saved template. Custom rows without template content retain one-click deletion. Acceptance: Cancel leaves the row and content intact; Delete removes only that custom type and remains removed after reopening. No general undo/history system in this scope.

Ship these alongside the editor basics; items 1–2 are planned, item 3 is a bounded optional addition. Syntax highlighting, template variables, extra presets and icon work do not enter this release through this decision. None of the three came from a user report: item 1 is a defect found in code review and then reproduced, items 2–3 are code-review opportunities. Status: item 1 is implemented in #27; the editor basics, item 2 and item 3 are not implemented. Release validation is pending for all of it.

- **Menu labels for custom + renamed types (issue #2)** — SHIPPED in v0.2.2 (2026-09-02), option 2 of 3.   **Fix:** expose `displayName` as an editable field in `FileTypeRow`, and default new custom types to a derived label instead of the hardcoded string. Rejected: deriving the label from `baseName`+`ext` and dropping the field (would rewrite built-in labels shipped since v0.1.0 — `.md` is labeled "New Markdown" but creates `Untitled.md`; `.env` is labeled "New .env" and creates `.env`); and deriving only for custom types (leaves the built-in-rename report unfixed).
  **Satisfies all three reporters:** [cat11meow](https://github.com/mariusgm/newfile/issues/2) (opener), [luiscruvinel](https://github.com/mariusgm/newfile/issues/2#issuecomment-5025920961), [Ballou](https://github.com/mariusgm/newfile/issues/2#issuecomment-5313785845) — the last is the built-in-rename case, not Tahoe-specific.

PR #1's test-plan line "Edit base name + template, OK/Cancel sheet round-trip" passed because it was checked against Preferences, which is exactly where the change *does* appear.

Options: (a) demote “Use it” to the OPTIONAL block alongside the toolbar button, (b) keep it as step 3, (c) fold the right-click instruction into the new step 2’s secondary line and keep `hasUsedAction` driving that step’s checkmark. Pick one; don’t silently delete the flag.

- **iCloud Drive: no right-click menu (issue #5)** — reproduced by the operator on macOS 27.0 (2026-10-05); documented in README + setup window in v0.2.4, no code fix. When this started is **not established** — the forum report dates it to Sonoma, but iCloud-related Finder Sync reports predate that.   **SPIKE DONE 2026-11-21 (draft PR #28, evidence only, never merges).** Tested configuration: one Mac on macOS 27.2.1, a Developer ID build, iCloud Drive on, Desktop and Documents not synced to iCloud. Two routes were tried with real right-clicks in an iCloud Drive test folder; the extension and the service handler logged every callback.
  - **Route 1, registering the iCloud Drive paths in `directoryURLs`: failed on the tested configuration.** Three variants: `/` alone (what ships), `/` plus `~/Library/Mobile Documents/com~apple~CloudDocs`, `~/Desktop` and `~/Documents`, and those three paths without `/`. In all three, Finder showed no NewFile item on empty-space or selected-folder right-click (4 right-clicks per variant) and never called `menu(for:)` inside iCloud Drive. With `/` claimed, Finder does send `beginObservingDirectory` for iCloud Drive folders, so the folders are observed and the menu is still withheld. Claiming only the iCloud paths also removed the menu from local folders. Other macOS versions and iCloud-synced Desktop/Documents were not tested. **No further retries without new evidence** (for example a different result reported on another macOS version, or a statement from Apple).
  - **Route 2, a Services entry ("New Text File Here", `NSSendFileTypes` = `public.folder`, handled by the host app): worked for a selected folder.** Four files were created inside the selected iCloud Drive folder: two from the folder's right-click menu, two from Finder → Services. **Sandbox, as observed:** the host app has only `user-selected.read-write`; all four writes succeeded and no sandbox denial was logged.     - **Selected folder only.** It was not offered on empty-space right-click, and the file lands inside the selected folder, not in the folder the window shows.
    - It is a Services item, not NewFile's own menu: one fixed file type in the spike, no submenu of the user's types.
  - **Verdict:** the exit criterion (a right-click path that creates a file inside an iCloud Drive folder, reproduced twice) was met by Route 2 for a selected folder only. This is a partial workaround; the ordinary right-click menu inside iCloud Drive is not restored and no route for it is known.
