# CLAUDE.md — NewFile

NewFile is a native macOS utility (app + Finder Sync extension) distributed as a signed, notarized DMG and via a Homebrew tap. Craft track — judged by the craft-track bar (used ≥30d / teaches a skill / scratches a real irritation), **never** by the commercial Verdict Machine.

## The two-repo rule (most common mistake)

**Every release touches TWO repositories:**

| Repo | Holds |
|---|---|
| `mariusgm/newfile` (this one) | app source, `project.yml`, the built DMG under `release/` |
| `mariusgm/newfile-site` | the marketing site **and the Sparkle appcast** |

Shipping a version here without updating the appcast in `newfile-site` means existing users never receive the update. The site deploys on **Cloudflare Pages** (CF CI auto-deploys on push) — not Vercel. There are no GitHub Actions workflows in this repo; do not look for release CI here.

## Build

Project is generated by **XcodeGen** from `project.yml` — edit that, never the `.xcodeproj` directly (it is regenerated and your change is lost).

```bash
xcodegen generate          # regenerate NewFile.xcodeproj from project.yml
xcrun xcodebuild -scheme NewFile -configuration Release
```

Version lives in `project.yml` (`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`), currently 0.2.4 / 6 on branch `release/0.2.4` (unreleased), Swift 5.10. Latest tag is `v0.2.3`. `release/` carries the archive, DMG, `ExportOptions.plist`, `resume-notarization.sh` and a per-version runbook — read the runbook before cutting a release.

## Release mechanics (verified 2026-09-02, v0.2.2)

- Notary keychain profile: `newfile-notary` — **returned HTTP 401 on 2026-10-06** and re-storing it from the ASC API key did not take effect (unexplained; repair deferred). v0.2.4 notarized with `capturelayer-notary` (ASC API key `7V85G54K6G`, team Q7VD7MTRL8 — registry: hub `services/app-store-connect-api.md`). Sparkle EdDSA key: keychain service `https://sparkle-project.org`, so `sign_update --account newfile` (default account fails).
- **Codesign the DMG before notarizing** (`codesign -s "Developer ID Application: …" --timestamp NewFile.dmg`), then submit → staple → `spctl -a -t install` = accepted. v0.2.1 and earlier shipped UNSIGNED DMGs (spctl rejected; worked only via the stapled ticket) — v0.2.2 is the first to pass Gatekeeper assessment.
- **Sandboxed host + Sparkle needs the mach-lookup exceptions** (`<bundle-id>-spks` / `-spki` in `App/NewFile.entitlements`). Without them every update dies with "installation data was never received" (bootstrap lookup denial, xpc error 159) — auto-update was broken from v0.1.0 until v0.2.3, and 0.2.1/0.2.2 users must update manually once. Test any updater change against a loopback appcast (serve a signed zip + appcast on localhost, `defaults write` SUFeedURL into the app container) BEFORE publishing.
- **Kill the old app process before install-testing a new build** — `osascript quit` fails silently when a dialog is up; a stale process runs the old binary and invalidates the test (`pkill -9 -f NewFile.app`, then verify pid churn).
- **Publish TWO assets per release — the appcast enclosure must NOT point at the DMG.** Through v0.2.3 the appcast enclosure pointed at the same `NewFile.dmg` humans download from the site, so Sparkle's automatic background updates incremented the *identical* GitHub download counter as first-time installs, and the two are not separable from GitHub's API. From the next release on: `NewFile.dmg` for humans / Homebrew / newfile.dev, and a separate `NewFile-update.zip` (zipped `NewFile.app`) as the appcast enclosure only. Sign the zip with `sign_update --account newfile` and use its own `length` + `sparkle:edSignature` in the appcast item. This splits the counters permanently: DMG count = manual-download traffic (still includes repeat downloads and reinstalls — not an install count), zip count = automatic update traffic. Do not "simplify" it back to one asset — the single-asset shape is what corrupted the traction series on 2026-09-02.
- **Release order (v0.2.4 onward):** archive → Developer ID export → zip the app, notarize, `stapler staple` the **app** → from that one stapled app make BOTH artifacts: `ditto -c -k --keepParent NewFile.app NewFile-update.zip` (Sparkle enclosure, signed with `sign_update --account newfile`) and the DMG (`create-dmg`, codesign, notarize, staple). The ZIP that passes the loopback test is the exact file that gets published — never regenerate it after testing.
- **Rollback before any install test:** `ditto` the installed app to `~/Backups/newfile-<ver>-rollback/` and `codesign --verify --deep --strict` the copy. Settings live in `~/Library/Group Containers/Q7VD7MTRL8.dev.newfile.NewFile/` and `~/Library/Containers/dev.newfile.NewFile/` — **the Claude Code shell cannot read either (TCC; `defaults export` returns an empty dict)**, so the operator quits NewFile and copies the Preferences folders in Finder.
- **Loopback update test — the SUFeedURL override must be written by the operator in Terminal.app** (same TCC wall): first `defaults read <container prefs path> SUFeedURL` to record any existing override, then write the localhost feed, test, and `defaults delete` (or restore) afterwards; confirm the app is back on `https://newfile.dev/appcast.xml`.
- sign_update lives under DerivedData `SourcePackages/artifacts/sparkle/Sparkle/bin/` — deleting DerivedData removes it until the next build.

## Known traps

- **App Group IDs need the Team-ID prefix.** Omitting it makes macOS re-prompt for permissions on every launch. This was the fix that shipped in v0.2.1 — do not regress it.
- **Notarization entitlement debt:** the appex ships a broad temporary exception entitlement. It notarizes today, but it is the most likely cause of a future slow-lane review or rejection. Treat any notarization slowdown as this, first.
- **No Resend, no email in this repo** (verified 2026-07-13). If a task seems to need transactional email, it is the wrong repo.

## Roadmap

- **Menu labels for custom + renamed types (issue #2)** — SHIPPED in v0.2.2 (2026-09-02), option 2 of 3. Three reporters, one root cause: `displayName` is write-once and unreachable from the UI, while the menu renders only it (`Extension/FinderSync.swift:129`). `App/PreferencesView.swift:31` hardcodes `displayName: "New file"` for every custom type, and `FileTypeRow` exposes only `enabled` / `ext` / `baseName` / `template` — so custom types are permanently "New file", and editing a built-in's base name changes the created filename but never the menu label.
  **Fix:** expose `displayName` as an editable field in `FileTypeRow`, and default new custom types to a derived label instead of the hardcoded string. Rejected: deriving the label from `baseName`+`ext` and dropping the field (would rewrite built-in labels shipped since v0.1.0 — `.md` is labeled "New Markdown" but creates `Untitled.md`; `.env` is labeled "New .env" and creates `.env`); and deriving only for custom types (leaves the built-in-rename report unfixed).
  **Satisfies all three reporters:** [cat11meow](https://github.com/mariusgm/newfile/issues/2) (opener), [luiscruvinel](https://github.com/mariusgm/newfile/issues/2#issuecomment-5025920961), [Ballou](https://github.com/mariusgm/newfile/issues/2#issuecomment-5313785845) — the last is the built-in-rename case, not Tahoe-specific.
  **Test gap to close with it:** nothing covers the settings→menu-label binding; `Tests/PlumbingTests.swift` is an `XCTAssertTrue(true)` stub and the 26 existing tests all sit below the extension. PR #1's test-plan line "Edit base name + template, OK/Cancel sheet round-trip" passed because it was checked against Preferences, which is exactly where the change *does* appear.
- **In-app uninstall affordance (DMG users)** — SHIPPED in v0.2.2 (`App/UninstallHelper.swift` + app-menu item). Disables the appex (`pluginkit -e ignore`), kills the running instance, optionally removes the group container, reveals the app for drag-to-Trash, quits. MAS-edition note: the `pluginkit`/`pkill` calls won't survive App Sandbox review — gate the menu item out of that build. Cask `zap` already covers all four containers (verified 2026-09-02; the v0.2.1 runbook's pending-note was stale).
- **Split the Sparkle enclosure off the DMG** — committed, do in the next release (see Release mechanics). Until it ships, post-0.2.3 DMG download counts are an upper bound on installs, not an acquisition metric, and are not comparable to the pre-0.2.3 series.
- **Setup window step 2 → “Add and customize file types”** — BUILT on `release/0.2.4` (2026-10-05), option (c): right-click instruction is step 2's secondary line, `hasUsedAction` still drives the checkmark, the button is prominent only once the extension is on and unused. Original note follows. Today step 2 is “Use it” (`App/ContentView.swift:62-70`), a passive instruction with no button; the customization layer — the thing that makes NewFile more than a right-click .txt — is only reachable from the app menu, so a first-run user never learns it exists. Change step 2 to **“Add and customize file types”** with a primary button that opens Preferences via `PreferencesWindowController.shared.show()` (already a singleton, already used by the `openPreferences` distributed notification — no new window plumbing).
  **Open decision before implementing:** what happens to “Use it”. Its `hasUsedAction` flag (`SetupStatus`, fed by the `toolbarOrMenuUsed` distributed notification) is the *only* in-app proof the extension actually fired end-to-end — dropping the step drops that signal from the setup window. Options: (a) demote “Use it” to the OPTIONAL block alongside the toolbar button, (b) keep it as step 3, (c) fold the right-click instruction into the new step 2’s secondary line and keep `hasUsedAction` driving that step’s checkmark. Pick one; don’t silently delete the flag.
  **Design gate:** `native-app-design` skill, per § Design — a second prominent button in the step stack competes with step 1’s “Open Login Items & Extensions”, so the new button should be non-prominent while the extension is still disabled.
- **iCloud Drive: no right-click menu (issue #5)** — reproduced by the operator on macOS 27.0 (2026-10-05); documented in README + setup window on `release/0.2.4`, no code fix. Finder shows no third-party Finder Sync contextual items inside iCloud Drive (incl. iCloud-synced Desktop/Documents); the toolbar menu still works there. Apple DTS: Finder Sync isn't a general Finder plug-in, and when two extensions claim a folder Finder "picks one" ([thread 737283](https://developer.apple.com/forums/thread/737283), [766680](https://developer.apple.com/forums/thread/766680)). When this started is **not established** — the forum report dates it to Sonoma, but iCloud-related Finder Sync reports predate that. We haven't identified a supported Finder Sync workaround that restores the right-click menu; registering the iCloud paths explicitly was not tried. Other integration points (Quick Actions / Services) remain possible and unexplored. **Revisit if macOS behavior changes or a reproducible workaround emerges.**
- **RTF built-in type (issue #4)** — BUILT on `release/0.2.4`: preset `rtf`, base name `Untitled`, template `{\rtf1}`, off by default. Existing stores get it from `SettingsStore.ensureBuiltIns`, which runs on **every read** and appends any missing built-in (off). A one-shot schema-3 step that skipped users with a custom `.rtf` shipped in the first 0.2.4 candidate and stranded the operator with no RTF type after deleting the custom one (walkthrough 2026-10-06) — built-ins can't be deleted or have their extension edited in the UI, so a missing built-in is never a user choice. A custom type with the same extension is kept alongside. **Release gate:** create a file through NewFile with this type, then open, edit and save it in TextEdit. Unit tests and format reasoning do not replace that check.
- **Template variables** (`{{filename}}`, `{{date}}`, `{{year}}`) — candidate, not committed. Needs resolution in the extension's create path; static templates are a valid first release without it.
- **Official Homebrew cask** — submit to `homebrew/homebrew-cask` when GitHub stars + downloads make notability clear. Not yet (30 stars / 1,259 DMG as of 2026-09-02).
- **Mac App Store edition ($2.99)** — same core app, no artificial limitations in the free build. Positioning: "NewFile remains free from GitHub. Buying the App Store edition supports continued development and provides App Store installation and updates." Decided 2026-08-20. Blocker: verify FinderSync extension write entitlements work under full App Sandbox (competitors like NewFileMenu ship on MAS, so likely feasible).
